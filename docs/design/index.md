# Nova 的设计

Nova 的设计从一个问题出发：当 Agent 的工作跨越多轮对话、工具与文件时，谁负责保存状态，谁负责向使用者解释发生了什么？

## 一个核心

C++20 运行时是项目的核心。目标是让会话、Agent 与工具调用在明确的职责边界内协作，并为正在进行的任务留下可追踪的状态。这是设计方向，不是对当前原型完整性的保证。

```text
任务输入
   ↓
Nova 运行时：会话 · Agent · 工具
   ↓
Web · 终端工作台 · 脚本 CLI
```

## 三种入口

| 入口 | 适合的工作方式 |
| --- | --- |
| Web | 浏览会话、观察过程、处理交互。 |
| TUI | 在终端中用键盘跟随同一份工作状态。 |
| CLI | 将任务接入脚本和已有命令流程。 |

入口的形态各不相同，但都应面对同一套运行时语义。让界面决定核心状态会导致行为分叉；因此设计先明确状态和边界，再逐步对齐各端实现。

## 为什么还要验证

系统设计只有在失败、取消、重启和并发场景下仍说得通，才算真正可用。Nova 正在用契约与回归场景持续检查这些边界。当前阶段见 [进展页](/progress/)，更完整的讨论见 [一个运行时，三种入口](/posts/one-runtime-three-surfaces)。
